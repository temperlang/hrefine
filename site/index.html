    The fix: decide with Hrefine, hand on href

    Hrefine doesn't change how your HTTP client reads URLs. So check the URL Hrefine parsed, then pass on its href, never the original string:

    • Parse once, with Url.parse, which gives null for anything that isn't a URL.
    • Check the parsed parts: scheme, hostKind (a name, or an address however it's written), and hostname.
    • Hand on href, the standard's canonical form: no backslashes, tabs, or odd address forms left to disagree on.
    • Check redirects too, or turn them off. For a next parameter, resolve it against your own site and check sameOrigin.

    Given href, the parsers agree

    The same parsers, given each of the recorded URLs as typed, and then given Hrefine's href for each URL Hrefine accepts: how often each reads the same host (or path, for path tricks) as the browser.

    Java's URL and curl refuse javascript:, a scheme they don't fetch, which is fine. The rest are paths: C# decodes escaped dots (%2E%2E%2F), and a % without hex digits, which href keeps as it is (/%zz), is refused by Java's URI and Go, and escaped again by C#. Java's URI follows RFC 3986, which also rejects a few characters href leaves as they are (such as | and ^); a strict form of href for such parsers is planned.

    Same tests. Same answers. Every language.

    • URLs, with and without bases, each with every part it must parse to, or a failure (urltestdata.json).
    • 2,760 of 2,762 international domain names (toascii.json and IdnaTestV2.json). The other 2 need unpaired surrogates, which Temper strings can't hold, so they're left out.
